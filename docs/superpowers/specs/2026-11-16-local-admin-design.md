# 数据底座本机管理台设计

状态：待用户审阅。本文描述拟实现的行为。

## 用途与部署

使用者在自己的电脑上核对接口定义、实际入库数据与采集状态，在同一处调整常用配置。启动方式沿用 `python scripts/start-project.py`，浏览器通过现有的 `127.0.0.1` 端口访问 `/admin`。关闭浏览器后，底座照常工作。

用户选择把管理台接入本机启动器。启动器已经负责绑定回环地址，以及启动 API、调度器和新闻进程。另一种方案是另起本机管理服务，好处是可以独立升级，代价是多一个端口和进程，且仍须与调度器通信。单人本机使用优先考虑一次启动。

由本机启动入口显式挂载页面和管理接口。默认 FastAPI 应用及服务器 Compose 入口继续只提供原有服务，公共 OpenAPI 合同独立于管理路由。建议采用随项目提供的静态页面，复用 FastAPI 端口，免去常驻前端开发服务器。管理请求限制本机 Host，写操作须校验同源及防跨站请求凭据，防止其他网页借本机浏览器操作任务。

## 查接口、查表与查任务

- **接口文档**提供公共接口目录、请求参数和响应结构，链接现有 Swagger UI 与仓库内业务口径文档。本机页面须能打开所链接的说明。文档采用当前代码版本，历史审计日期按原文保留。
- **数据表**按 PostgreSQL schema 展示本项目各应用表。选表后显示列名、类型、已有说明和一页真实记录，可前后翻页。说明缺失时标明暂无说明。按主键或可用的稳定唯一键分页；有索引支持且日期含义明确时可按日期倒序，同日期按唯一键排序。缺少稳定键时显示普通分页及顺序提示。空表仍展示字段。实现建议默认每页 25 条，长文本和大型 JSON 按需展开，列表响应限制大小。用只读事务查询，从数据库目录校验表和列，禁止提交任意 SQL。页面打开时只取所选表的一页，无需为所有表精确计数。
- **定时任务**显示每项的用途、实际日程、开关、调度是否已应用、最近运行结果和时间。运行详情优先显示已有阶段、游标、处理量与更新时间；有可信总量才显示百分比。调度器心跳、新闻进程状态、单次任务记录分别取证，过期心跳或遗留的 `running` 显示状态待确认。没有历史或进度证据时如实显示。内务作业可以说明用途，只有现有九个业务开关可编辑。
- **从任务看数据**按可信的运行编号、批次键及已有映射定位记录，说明对应的是该批处理的数据；只有能证明插入时才标为新增。缺少关联时提供相关表入口，打开常规表预览。单靠时间相近不足以判定归属。

## 修改与应用

编辑表单为草稿，点击“应用”才校验并写入对应字段，随后请求运行方应用。界面分开显示文件保存结果、当前生效值和应用结果。实施建议首版覆盖以下范围，以单个配置文件为一次提交单位。

| 表单范围 | 配置来源 | 生效方式 |
| --- | --- | --- |
| 新闻和八项日周任务开关 | `config/scheduled-tasks.json` | 启动器协调新闻进程及共享调度器，目标任务确认后显示已生效 |
| 市场任务的共用日程时间 | `config/market/market-data.json` 的 `schedule.time` | 展示受影响的任务组，更新已启用任务的下一次日程，在途任务继续 |
| 新闻轮询间隔 | `config/news/news-collector.json` 的 `interval_seconds` | 运行中的新闻进程下轮读取后确认；关闭时提示下次启用时读取 |

股票及公告的共享日程、宏观周日程首版展示实际配置和来源，继续支持原有文件配置方式。页面不提供通用文件编辑器。文件写入须保留其他字段，校验读取时的版本并原子替换，遇外部编辑冲突时提示重新载入。只暴露表单所需字段。配置未通过校验时保留原值。文件已保存但进程未确认时显示待应用或具体失败原因，并支持按同一版本重试。任何修改均不会自动重启整个底座。

## 任务启停与缺口恢复

本机启动器需能在 API 已运行时增减受管子进程，区分按需退出与异常退出。共享调度器需接收逐项变更并报告实际日程；现有启动时读取的环境变量不足以完成此操作。新闻使用独立的 `watch-news` 循环，需要支持本轮完成后退出。进程间通信方式交由实施者决定。

- **关闭**后禁止该项再开始一轮定时执行或补采，含已排队但尚未执行的轮次。正在执行的本轮正常收尾，页面显示“本轮运行中，后续调度已关闭”。其他任务的调度、心跳及 API 连续运行。最后一项关闭时待在途工作结束后再回收空闲进程。
- **恢复**仅在目标任务从关闭切换到开启时，自动按其能力检查并补采暂停期间的缺口。复用交易日历、检查点、新闻游标、任务锁和各来源原有的限额。只触发目标项的恢复逻辑。若首次启用时需要启动调度器，与启动补采去重。重复点击、刷新页面、仅改日程和应用结果重试都不得重复启动同一轮补采。项目正常冷启动沿用已有恢复策略。
- **反馈**区分已补齐、仍有积压、失败、仅能更新最新数据，以及证据不足。超过单轮预算时保留检查点，显示实际可知的剩余范围和后续处理方式。已经积压的历史若来源无法回补，要让使用者看到覆盖边界。运行中的补采与定时触发共用该项已有互斥与限流机制。
- **恢复与并发**按最新已保存的目标状态和工作进程实际状态协调，按任务串行处理启停。在途期间再次打开，应保留单个工作实例；进程确认丢失时先查已生效版本和任务记录。采用与既有恢复记录兼容的幂等标识处理重试。实现者可选回执存储和控制通道，若需新增持久化对象，实施计划须列出迁移及部署影响。

## 验收场景

1. 本机按原命令启动，任务全关也可查接口、浏览各表和字段；独立启动的公共 API 访问管理地址无此路由。其他网站发起的管理写请求被拒绝。
2. 预览空表、复合主键表和含长 JSON 的表。翻页不全表加载，未提供说明的列仍可查看实际值。分别验证可按批次追溯和只能定位到表的两种任务。
3. 一个任务正在执行时将其关闭，确认其本轮完成且下一轮不启动；并行核对另一项日程及 API 仍可用。新闻和共享调度器分别覆盖首次启用、全部关闭及收尾时重新开启。
4. 以暂停数日的任务验证自动检查、实际可补的范围和结果。覆盖无缺口、超限、缺少历史能力，以及启动与定时触发相邻的情况。重复应用不能重复采集。
5. 分别验证配置文件冲突、进程确认失败、应用重试，以及新闻下一轮读到新间隔。文件已保存时，页面仍以工作进程确认为生效依据。
