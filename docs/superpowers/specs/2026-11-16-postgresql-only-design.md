所有需要持久化到数据库的功能使用 PostgreSQL。本次升级目标是项目当前写连接 `DANG_DATABASE_URL` 指向的库。已有业务数据继续就地使用。数据库测试使用独立的临时 PostgreSQL 实例。业务 JSON 配置、外部导入文件仍由原功能管理。

用户已选定把本机管理状态、执行历史及存在的旧新闻记录迁入当前主库。以提交 `bd44bbf` 和当前工作区为基线，2026-11-16 只读核对了配置指向的两个存储。PostgreSQL 的 `alembic_version` 为 `20261116_0022`，已有 `ops.data_acquisition_state`，待建的两张本机管理表均未建。本机控制库有 9 条任务状态、0 条执行记录、0 个活跃任务，配置指向的旧新闻文件不存在。切换时重新盘点，用实际读数验收。

## 运行方式

通过现有 Alembic 版本链，在 `ops` 增加 `local_admin_task` 和 `local_admin_execution`。保留任务名、启停、规则、代次、配置修订、补跑标记、工作进程确认、起止时间、执行结果、错误和下次调度时间。保留执行记录原 ID 和按任务倒序翻页，并校准后续 ID。新表由版本迁移创建，应用复用 SQLAlchemy 与 psycopg 的连接方式。

两张表分别按任务和领取轮次记录。前者让管理界面区分“已保存，待应用”和“已生效”，并供工作进程领取任务。后者记录从领取到结束的结果，例如证券日同步的一次启动补跑可以覆盖多个交易日，也可能在采集前失败。管理接口已有两个字段：`localRuns` 返回这些轮次，`runs` 从 `ops.job_run` 返回业务作业记录，包括请求数和写入行数。调度器的存活情况与检查范围沿用现有心跳表和检查点表。

现有 `ops.data_acquisition_state` 按 `entry_id`、`item_id`、`subject_kind`、`subject_key`、`scope_kind` 联合标识一条获取状态。例如一次证券补跑有一条本机执行记录，却可能涉及多只证券、多个数据条目及不同的采集结果。配置是否生效、补跑是否被领取，以两张管理表为准；某项数据是否取得，以该对象和范围的采集凭证为准。迁入管理记录时只写管理表。旧新闻队列的迁入也不能据此产生一次新的来源采集成功记录。

新迁移接在 `20261116_0022` 之后。两张新模型若登记到 `Base.metadata`，同步补入初始修订 `0001` 的 `OWNED_LATER`，由新修订独占建表。为新修订更新备份校验的 `GUARD_COUNTS` 登记，沿用当前 5 组企业证据保护规则，并更新迁移头与恢复演练的版本断言。

`ControlStore` 继续服务于本机父进程、新闻和调度子进程。每个进程用配置取得写连接，父子进程通过已有控制模式标识协调运行。以同一事务内的条件更新和执行记录插入实现任务领取，拒绝失效的配置版本、重复的补跑及并发领取。完成或异常恢复只结算相应的执行记录。每个目标库同时只允许一个本机管理父进程操作这组共享任务，使用项目现有 PostgreSQL advisory lock 机制；在取得管理权后才执行启动恢复。覆盖正常退出、进程失联、重新启动及父进程丢失数据库锁的情形。

按用户选择，移除采集包的独立命令注册、模块命令行入口、专用参数和对应使用说明。保留项目调用的采集库和可注入的 Store 接口。项目的 `watch-news`、`sync-news`、`news-status` 和定时采集沿用主库的 `ops.job_cursor`、`ops.news_delivery` 以及现有去重、确认和发布流程。Alembic 负责数据库初始化。

项目新闻入口的 `save_health` 在写入健康游标的同一事务调用 `record_news`，为新浪财经来源记录检查结果。移除旧文件读取与迁入逻辑时保留此调用及其时序。同轮采集成功后若交付失败，状态查询应显示交付失败；分页未结束时继续显示凭证不足。

数据库连接、只读会话、约束、锁、查询及迁移使用 PostgreSQL 语义；保留历史 Alembic 修订号和 PostgreSQL 升级路径。纯文件校验（如 `validate-import`）直接复用文件解析和校验逻辑，支持无数据库连接执行。

数据获取模块的数据库适配涉及以下路径（相对于 `backend/app/acquisition/`）。

| 文件 | 切换到 PostgreSQL 后需要保留的行为 |
|---|---|
| `repository.py` | 用冲突插入与行锁处理并发，按开始时间和尝试 ID 拒绝迟到的旧凭证。 |
| `adapters/targets.py` | 用带时区的时间解码和校验原件，根据已登记对象、实际候选和请求记录判定指数与 ETF 的状态。 |
| `availability/stored.py` | 用 JSONB 查询公告关联证券，按上海时区的数据期边界判断公告是否可用。 |
| `service.py`、`macro_compat.py` | 状态查询使用可重复读的只读事务；宏观审计在实际 `ops` schema 检测凭证表，并按目录版本、系列和时间选择可信凭证。 |

## 切换与数据核对

1. 在隔离库演练空库安装、从当前版本升级、带历史的迁入和重复执行。对实际库切换时，记录原服务和任务启停状态。停止可能写入的管理、调度和采集进程，等待在途事务结束。保存可恢复的切换前数据，记录获取状态表按五列主键稳定排序后的行数和内容摘要，以及已发布产品的当前版本。在停写期间固定 StatusService 的 UTC 读取时刻，对代表性对象、数据期和发布版本保存查询结果。
2. 确认目标库身份和迁移版本，应用增量迁移。在新管理进程首次启动前，用一次性工具一致读取旧状态，在事务中导入两张管理表。按任务名和执行 ID 核对所有字段，规范化布尔、空值和带时区时间，保留记录之间的对应关系。重复运行认可已核对的相同数据，发现目标键冲突且内容不一致即回滚并报告。
3. 若发现旧新闻文件，核对已有迁入回执及目标游标、事件、队列的投递状态，复用已验证的迁入语义，防止覆盖较新的主库状态或重复投递。源文件缺失时直接使用当前主库中的新闻数据。任何来源未能核对时保留原文件，记录差异。
4. 管理记录导入提交后、服务恢复前，通过新连接复核获取状态表摘要和发布版本，并逐条复核导入的任务及历史。以步骤 1 的同一读取时刻和查询条件重查服务层，比较采集结果、可用性和审计结论，消除公告公开时间和宏观序列有效期跨界的影响。历史凭证初始化命令 `reconcile-data-status` 默认只读，切换本身无需执行 `--apply`。恢复原先启用的服务后再查管理页、进程与新闻队列。通过公共 `GET /api/v1/data-status` 与本机 `GET /admin/api/data-status` 验证 HTTP 查询、分页和响应结构。此时状态反映实时读取时刻与恢复后的采集进展。失败时保留原始数据和已提交阶段的回执，可从核实的阶段重试。
5. 核对成功后移除项目内旧库文件、已识别的临时测试库和一次性迁入工具。清理代码、旧连接选项、环境样例及本机配置中的废弃键、Compose 挂载、测试、脚本和项目维护的文档。以工作树和本机项目产物为清理边界；第三方安装环境和 Git 对象历史有独立生命周期。

- 复用现有 PostgreSQL 17 测试容器机制，把需要数据库的测试迁入隔离库，覆盖原有断言；纯逻辑测试继续离线执行。测试入口屏蔽项目业务连接和真实采集请求，支持同一测试多次连接、子进程共享，以及不同测试并发运行。
- 使用真实 PostgreSQL 验证迁移、只读事务、约束、时间比较、锁、任务抢占与崩溃恢复。覆盖保有历史执行记录的源、重复迁入和导入失败回滚。验证旧测试和新入口通过同一套测试命令运行，记录通过数、跳过项与原因。

- 搜索项目维护的文件内容、文件名、配置键和镜像挂载，检查无旧实现、路径、文档说明和项目生成的旧数据库文件。确认纯文件校验、已有迁移版本升级以及仅配置 PostgreSQL 的新安装均可使用。
