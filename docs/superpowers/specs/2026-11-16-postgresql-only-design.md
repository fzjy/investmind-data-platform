# 统一使用项目现有 PostgreSQL

## 目标与范围

所有需要持久化到数据库的功能使用 PostgreSQL。本次升级目标是项目当前写连接 `DANG_DATABASE_URL` 指向的库。已有业务数据继续就地使用。数据库测试使用独立的临时 PostgreSQL 实例。业务 JSON 配置、外部导入文件仍由原功能管理。

用户已选定把本机管理状态、执行历史及存在的旧新闻记录迁入当前主库。2026-11-16 只读盘点发现本机有 9 条任务状态、0 条执行记录、0 个活跃任务，配置指向的旧新闻文件不存在。切换时重新盘点，用实际读数验收。

## 已考虑的方案

| 方案 | 代价与结果 |
|---|---|
| A．把本机状态并入当前主库（用户已选） | 对当前库增加两张运维表。保留现有连接及业务数据，迁移范围限于原先存放在本机的记录。 |
| B．创建另一套 PostgreSQL 库 | 需复制所有业务与运维数据，对照新旧库并协调所有服务切换连接。适用于同时更换业务库。 |

## 运行方式

通过现有 Alembic 版本链，在 `ops` 增加 `local_admin_task` 和 `local_admin_execution`。保留任务名、启停、规则、代次、配置修订、补跑标记、工作进程确认、起止时间、执行结果、错误和下次调度时间。保留执行记录原 ID 和按任务倒序翻页，并校准后续 ID。新表由版本迁移创建，应用复用 SQLAlchemy 与 psycopg 的连接方式。

`ControlStore` 继续服务于本机父进程、新闻和调度子进程。每个进程用配置取得写连接，父子进程通过已有控制模式标识协调运行。以同一事务内的条件更新和执行记录插入实现任务领取，拒绝失效的配置版本、重复的补跑及并发领取。完成或异常恢复只结算相应的执行记录。每个目标库同时只允许一个本机管理父进程操作这组共享任务，使用项目现有 PostgreSQL advisory lock 机制；在取得管理权后才执行启动恢复。覆盖正常退出、进程失联、重新启动及父进程丢失数据库锁的情形。

项目内新闻继续使用 `ops.job_cursor` 和 `ops.news_delivery`，并沿用现有的去重、确认和发布事务。保留独立包的 `smartparse-news run/status/pending` 入口及可注入的 Store 接口。独立入口也使用 PostgreSQL，复用同一套状态和队列访问实现；通过连接配置获取地址，凭据不出现在命令行输出。底座工作进程与独立命令访问同一队列时遵守相同的并发控制，采集包可单独安装。代码放置和依赖拆分交由实施者决定。

为保留项目外独立使用的能力，仅安装采集包后也能在用户提供的空 PostgreSQL 库中初始化采集所需表，再执行上述三个命令。项目主库继续通过 Alembic 管理表结构。独立初始化和主库迁移使用一致的表结构，对已经完成项目迁移的库直接复用现有表；独立入口的验收同时覆盖空库和已迁移的项目库。

数据库连接、只读会话、约束、锁、查询及迁移使用 PostgreSQL 语义；保留历史 Alembic 修订号和 PostgreSQL 升级路径。纯文件校验（如 `validate-import`）直接复用文件解析和校验逻辑，支持无数据库连接执行。

## 切换与数据核对

1. 在隔离库演练空库安装、由当前版本升级、带历史的迁入和重复执行。对实际库切换时，记录原服务和任务启停状态，停止读取旧文件并可能写入的本机管理与采集进程，等待在途事务结束。保存可恢复的切换前数据。
2. 确认目标库身份和迁移版本，应用增量迁移。在新管理进程首次启动前，用一次性工具一致读取旧状态，在事务中导入两张管理表。按任务名和执行 ID 核对所有字段，规范化布尔、空值和带时区时间，保留记录之间的对应关系。重复运行认可已核对的相同数据，发现目标键冲突且内容不一致即回滚并报告。
3. 若发现旧新闻文件，核对已有迁入回执及目标游标、事件、队列的投递状态，复用已验证的迁入语义，防止覆盖较新的主库状态或重复投递。源文件缺失时直接使用当前主库中的新闻数据。任何来源未能核对时保留原文件，记录差异。
4. 在目标事务提交后通过新连接复核，再恢复切换前启用的服务。通过管理页面或接口核对九项任务的实际读数、执行历史和进程状态，核对已有 API、新闻队列和发布版本。实际运行造成的后续状态变化与首次导入结果分别记录。失败时保留原始数据和已提交阶段的回执，可从核实的阶段重试。
5. 核对成功后移除项目内旧库文件、已识别的临时测试库和一次性迁入工具。清理代码、旧连接选项、环境样例及本机配置中的废弃键、Compose 挂载、测试、脚本和项目维护的文档。以工作树和本机项目产物为清理边界；第三方安装环境和 Git 对象历史有独立生命周期。

## 验收

- 复用现有 PostgreSQL 17 测试容器机制，把需要数据库的测试迁入隔离库，覆盖原有断言；纯逻辑测试继续离线执行。测试入口屏蔽项目业务连接和真实采集请求，支持同一测试多次连接、子进程共享，以及不同测试并发运行。
- 使用真实 PostgreSQL 验证迁移、只读事务、约束、时间比较、锁、任务抢占与崩溃恢复。覆盖保有历史执行记录的源、重复迁入和导入失败回滚。验证旧测试和新入口通过同一套测试命令运行，记录通过数、跳过项与原因。
- 测试独立新闻 CLI 和宿主采集的队列、游标与修订语义，测试本机启动器、受管理的两个工作进程及 Compose 服务。用受控数据验证调度行为，实际库的验收采用读取和切换所需操作。
- 搜索项目维护的文件内容、文件名、配置键和镜像挂载，检查无旧实现、路径、文档说明和项目生成的旧数据库文件。确认纯文件校验、已有迁移版本升级以及仅配置 PostgreSQL 的新安装均可使用。
