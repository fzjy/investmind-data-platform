# 数据底座全域重构实施计划与交付记录

目标是让调用方按证券、日期、指标或事件独立查询底座数据，让 InvestMind 通过自己的适配层组合这些数据，并让每一次采集复用和存储调整都有可核对的依据。当前唯一登记的消费项目是 InvestMind。方案基于现有 Python、FastAPI、SQLAlchemy、PostgreSQL 和发布机制，按数据域交付，每批均能独立验收和回退。

本方案于 2026-11-19 获准实施。下表保留审批时的证据与待验证事项，便于对照本次交付。实际覆盖范围、处置结论、库存限制及验证结果见[整体验收](../../foundation-acceptance.md)和[全域盘点](../../foundation-audit/README.md)。原始依据见[股票日频试点](../../stock-datasets.md)、[全域目录](../../data-catalog.json)、[字段消费者清单](../../field-consumers.md)和[历史结果留存说明](../../derived-history.md)。

## 一、现在能确认什么

| 要验证的能力 | 已有证据 | 推广前需要补的证据 |
| --- | --- | --- |
| 按数据集查询 | 股票日线、复权因子、每日估值已支持单股区间和单日截面。首轮在 50 股开发库存上，以独立 SQL 对账 111,007 行，833,649 个非空数值和 17,138 个空值全部一致。 | 日频试点读的是当前库存。事件修订、宏观数据在历史时点的可见性、新闻展示范围等分别验收。 |
| InvestMind 组合数据、保留产品接口 | 股票快照输入与新接口已经复用同一日频查询。36,037 根复权日线、50 股的报价和选股字段已与已发布结果核对。 | 目前只打通了部分输入。例如工作台指标卡仍自行查询最近行情并关联当日估值。全过程应覆盖这些旁路，也要覆盖其他域的快照、实时读取和混合响应。 |
| 识别重复并决定是否更改 | 分红有 156 次相同请求及相同正文的额外捕获，也有 54 个请求键出现不同正文。405 个事件从专项数据取得了标准记录缺少的实施或股本字段。 | 数据库足以证明重叠。实际可省请求数须按当时的任务和凭证逐次还原。物理合并还要证明留存、发布摘要、恢复和消费者均等价。 |

建议采用**逐域切换**。一次性重写会把数据口径差异与迁移故障混在同一次验收里。仅增加 HTTP 包装会留下各个产品各自读表、各自选版的问题。逐域方案允许某项事实先开放查询，同时让证据不足的采集和存储继续工作。

## 二、目标边界

| 环节 | 承担的责任 | 在当前项目中的落点 |
| --- | --- | --- |
| 采集与凭证 | 保留上游请求范围、字段、原件、捕获时间和任务结果。多个任务可以引用同一份合格凭证，并分别记录覆盖情况。 | 从各域已有采集入口、Raw 和 `backend/app/acquisition/` 的绑定及凭证入手。 |
| 领域数据集 | 每个可独立解释的主题定义业务键、单位、时间含义、修订规则和来源。优先读取已验证的标准事实，专项独有的事实经核对后接入。 | 延续领域内查询函数和模型。股票试点在 `backend/app/stocks/dataset_query.py`。复杂主题优先复用现有领域函数。 |
| 公共查询 | 对可独立使用且允许提供给其他项目的主题，在 `/api/v1/datasets/` 下按数据集开放只读查询。请求只读取库存。 | 参考 `backend/app/stocks/datasets_routes.py`。一个业务数据集可来自多张表，一张表也可包含多个业务主题。每个供应商接口、每张物理表和每个页面指标均单独评估是否需要公开。 |
| InvestMind 适配层 | 在服务进程内批量调用同一套领域查询，处理跨数据集关联、公式、展示精度、页面字段和状态。现有 URL 继续供 InvestMind 使用。 | 在各域构建器、服务和 provider 中归拢产品专属逻辑。快照型产品在发布时组合，同步读库的产品在请求时组合，混合接口分别保留各部分时点。领域查询可以接收调用方事务，避免跨页 HTTP 拼装产品。 |

**例子。** 公共日线给出未复权价格，复权因子按自己的交易日返回。InvestMind 用股票、日期和窗口末端基准生成复权 K 线。公共分红则给出有来源的事件、金额和阶段。工作台计算股息率时采用的财年与预测窗口属于 InvestMind。调用方可以只取其中一种事实。

适配层的代码边界也要能验证。以股票为例，`stocks/datasets_routes.py` 负责公共请求，`stocks/dataset_query.py` 负责事实选取，`stocks/marts/prices.py` 等产品模块负责组合，`stocks/routes.py` 保持 InvestMind 的响应合同。各域遵循同样的依赖方向，公共查询能够脱离工作台和发布器运行。在 `backend/tests/test_domain_boundaries.py` 检查公共查询对产品层的反向依赖，在产品测试中验证真实发布入口确实调用共享查询。协议兼容还包括选股与研究的 POST、工作台的 GET 及其旧路径。

### 4. 按依赖顺序推广到整个底座

以下是建议顺序，候选接口的最终数量由步骤 1、2 确定。每一批都完成“事实定义 → 领域查询 → 公共 API 或内部用途说明 → InvestMind 适配 → 对账”。已经符合要求的条目可用现状和测试直接验收。

| 波次 | 覆盖对象与关键决定 | InvestMind 验收对象 |
| --- | --- | --- |
| A　证券、股票与财务 | 证券标识与别名、交易日历、分类及成员生效期优先；再覆盖财报、披露日历、股东、公司事件、估值长历史及其余股票条目。财报分别建模报告期、公告日、口径和修订版。普通估值与长期专项只在来源及覆盖规则明确后组合。 | 搜索、选股、研究和工作台。比较不同交易市场的代码、报告期内多版本、成分变更、空财务字段、老快照和指标输入来源。 |
| B　市场、指数、ETF 与商品 | 盘点各类行情、成分、地区和市场脉搏。区分交易日历、品种、合约、单位及交易状态，核对专项多出的状态字段。 | 市场概览、探索、排行和热力图。分别验证缺行情、缺交易状态、跨市场交易日，以及概览中另行读取的新闻。 |
| C　宏观 | 按指标序列、观测期、单位、发布日期和修订时间定义查询。复用 `backend/app/macro/api/observations.py` 已有的历史时点选版逻辑，核对常规与专项系列。 | 宏观传导和洞察，以及消费宏观数据的其他产品。挑同一观测期在修订前后的两个截止日重放，分别匹配对应版本。 |
| D　财经内容 | 盘点新闻、公告及其他已登记内容的来源、供应商标识、发布时间、展示条件、版本和留存范围。拆出可共享的可见内容读取，来源名称翻译、页面时间格式和采集健康状态由产品适配。 | 新闻列表、市场新闻、工作台公告。核对时区、相同时间戳翻页、不可展示和过期内容、来源延迟及现有新闻游标。 |

### 5. 每一批怎样验收和切换

1. **锁定接口合同。** 对每个公共数据集登记名称、业务键、可用字段、单位、空值、唯一排序、筛选组合、日期边界、分页和错误。区分当前库存、按历史时点可见的数据和已发布产品版本。公共查询直接取库存，采购渠道与原始字段在目录中保留可追溯关系。
2. **先写回归，再接入读取。** 用隔离 PostgreSQL 覆盖旧数据、精确小数、空值与零、空结果、重复参数、游标跨条件、缺凭证及有冲突的原件。新旧产品读取同一份冻结输入，在影子构建中对照；影子构建禁止提升正式发布指针。
3. **逐项比对。** 公共接口对照独立 SQL 的键、时间、值和来源，产品接口比较字段、排序、展示精度、版本、缓存和缺口状态。保留旧调用方使用的路径与参数，包括兼容路由。对照时固定版本、时钟和输入；随机请求标识等动态字段单独检验规则。相同合同下未解释差异应为零。记录典型查询的耗时、SQL 次数与分页计划，并验证逐股查询不会变成产品构建中的逐股 HTTP 调用。
4. **分域启用、可独立撤回。** 在隔离环境验证旧读取路径或上一发布版本可恢复，再按域切换。未发布的新路径可以直接撤回；已发布产品用既有版本机制恢复经核对的版本，实时接口恢复上一读取实现。采集复用出现问题可单独恢复原任务定时与请求路径，保留原件及已记录的凭证引用。其他域继续使用各自版本。
5. **同步交付目录。** 更新 `scripts/export-api-requests.py`、`scripts/export-data-catalog.py` 及相应领域定义，按变更范围生成 OpenAPI、请求示例、数据目录和字段消费者映射。复核实际注册路由、示例响应和管理台显示。每批附加一份对账与回退记录。

### 6. 最后处理确有收益的存储调整

实库逐项核对后，本轮采用统一读取和保留物理存储。专项分红补充字段、来源凭证、版本和快照均有实际消费者。下列条件性回填、写入切换和退役流程本轮无需启动。[表内、跨表与恢复用途](../../foundation-audit/README.md)

- [x] 从步骤 2 中挑出有一致性或维护收益的候选，例如多个任务各自写同一标准事实、两份可变副本可能分叉。逐项列出权威写入者、受影响的列、索引、约束、读写方、摘要、旧快照与保留用途。数据量不作为删减目标。
- [x] 若须改结构，按“先加新结构 → 可重试地回填 → 校验主键、逐字段值及来源引用 → 追平并发写入 → 切换读写 → 观察一个覆盖正常更新与修订的周期”执行。中途重试和重复执行都要收敛到同一结果。回退演练须证明切回旧读取后仍能看到切换期间新增或修订的记录。
- [x] 原件、业务事实、派生计算和发布快照可以分别承担不同职责。逐项处置结论可为永久保留、统一读取、停止重复写入、迁移或退役。涉及删除历史、删列删表的具体清单与备份恢复验证另行提交确认。全域架构可先完成迁移和切换，再决定物理退役。

## 四、审核后如何执行

建议一次批准上述范围和逐域策略，由同一工作会话按勾选项推进，先交付全域清单和分红实证，再逐批接入。遇到已有公开合同需要改变、历史可见性无法证实却需要对外承诺，或需要执行物理删除时，将具体影响及选项提交决定。每批的证据与结论随工作保存，可以集中审核。实际部署环境与发布时间在发布前确定。
