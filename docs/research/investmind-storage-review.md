## 2026-11-15 当前正文与历史版本

逐个比较 56 个当前指针与其同产品、同版本历史记录。6 个产品的 JSON 文本和业务时间完全相同，证券工作台其余 50 对的历史风险字段按原设计不随版保存。下列列大小是数据库当前压缩值，含索引的总实际节省另在隔离库测量。[逐产品版本、历史 ID 与数据库计量](investmind-snapshot-storage.json)

| 产品 | 同版历史 ID | 当前正文列字节 |
| --- | ---: | ---: |
| macro-insights | 932 | 325,758 |
| macro-transmission | 931 | 3,264,573 |
| market-explorer | 1879 | 91,313 |
| market-overview | 933 | 2,780 |
| portfolio | 1847 | 1,555,366 |
| screener | 1786 | 327,377 |

公共 `SnapshotRepository.read` 从当前指针直接取正文，`read_meta` 只取版本与鲜度，按版本访问使用 `PageSnapshot` 的产品、版本唯一键。组合、市场与宏观读取器外，市场、股票和组合的发布前检查也读取当前正文。发布器在同一事务内写结构化行、校验或插入历史、加行锁切换当前指针。相同版本的不同历史正文或业务日会失败；过时发布可以进入历史，同时保留较新的当前指针。工作台历史写入时过滤 risks，当前版本单独持有完整风险信息。新闻内容修订还会锁定市场探索与工作台历史并修改敏感正文。新闻留存按独立阶段依次处理历史与当前。股票风险回填也单独移除历史字段。

将真实 56 个指针及同版历史复制到一次性 PostgreSQL 17。快照历史表保持相同，试验仅将正文文本相等的 6 个当前指针改引用历史 ID，并为其余 50 个保留独立正文；引用表有外键和互斥检查。紧凑后的当前指针表含索引由 16,146,432 降到 10,362,880 字节，净省 5,783,552 字节。重组后的 56 个当前正文和全部元数据都与原值相符。

随后在隔离事务中只修改一条 market-explorer 历史正文，模拟历史清理先于当前阶段的操作。引用设计令当前产品立即显示此次历史修订，而现有存储在此步骤仍返回原当前正文。测试事务已回滚。真实发布、过时版本、回滚、时区、内容保留与风险回归共 39 项通过。**本次保留这 6 个实际当前指针的正文。** 若继续实施，须区分可共享的不可变正文与两个逻辑版本的修改，为历史与当前使用独立改写引用，并在发布和内容清理路径上验证原子切换。这里验证的容量和影响不构成已经迁移的记录。底座复跑入口为 `scripts/audit-snapshot-storage.py`。

### 逐产品能否共享历史正文

按当前运行源码，历史正文写者有发布器、内容版权修订、分阶段新闻留存，以及工作台专有的历史风险清理。发布器对相同版本重写会先核验原正文与业务日，一般情况下只追加历史；数据库本身没有禁止修改所有历史正文的约束。为判断适用范围，另在同一个只读事务中每八行一批检查六产品全部 287 条历史。

| 产品 | 全部历史 | 共享判断与调用条件 |
| --- | ---: | --- |
| market-explorer | 118 版均含 marketNews，103 版非空 | 内容版权修订与按期清理均会单独更新历史。保留可独立修改的两个逻辑版本；实时快讯的请求时间、来源和分页也独立于市场指针，不能按市场版本缓存实时快讯。 |
| macro-insights、macro-transmission | 各 58 版 | 116 版均无顶层 marketNews 及行情图公告字段。现有写者只追加历史，可在此合同下使用版本引用。必须保留宏观双指针原子切换、指定版本读取，以及网站按文档冻结已取版本的语义。 |
| market-overview | 15 版 | 无上述事件字段，可作为不可变正文候选。与市场探索联动发布时仍应在同一事务比较旧版本、完成质量门禁再切换当前指针。 |
| portfolio | 17 版 | 无上述事件字段，可作为不可变正文候选。组合 ETag 由产品合同及来源、鲜度、业务日、版本生成。条件请求已按指针元数据返回 304；共享后仍应在版本未变时避免加载任一正文。 |
| screener | 21 版 | 无上述事件字段，可作为不可变正文候选。选股对外的最新指针、无指针回退与结构化证券数据另有用途。备份程序直接从当前指针 JSON 的 stocks 计算行数；把指针正文直接清为空会将这项恢复证明误计为缺失。 |

后五项在当前数据合同和全部 169 条已存历史上没有独立修改历史的实际字段，具有按版本引用的条件。真正迁移应维持同一条 SQL 取得当前正文、旧版可查和发布失败整批回滚，并让备份解析指针引用。通用新闻留存仍可扫描全部快照；若将来五项之一增加事件字段，需要改成正文写入时复制或更新引用才能继续共享。市场探索保留独立写入；50 个证券工作台另外涉及风险字段，保持两个不同产品表示。

本轮另执行选股查询、组合条件读取、市场新闻投影、鲜度更新 14 项回归。此前实际网站重放也证实组合首次 200、三次 304 并且后续正文读取为零。空间引用用于减少数据库正文副本，不会减少必须取得新版数据的 HTTP 次数。
## 五项产品的当前正文复用已实现，并完成整库隔离恢复

独立底座迁移 `20261115_0021` 把合格的宏观洞察、宏观传导、市场总览、组合和选股当前正文改为对同产品、同版本永久历史的引用。迁移要求业务时间与 JSON 文本相同且没有顶层 marketNews 或 dailyChart。缺少同版历史、内容不同或将来新增事件字段时继续持有独立正文。市场探索和 50 个证券工作台继续独立存储。

指针正文列仍支持任意旧对象，引用在库内以 JSON 字符串表示。外键同时校验产品、版本和由历史正文计算的指纹，被引用的历史不能意外改写或删除。ORM、版本化 API 和仓内原生 SQL 审计都在一次查询内解析正文。组合条件请求继续只读元数据。宏观同步状态原本只需版本和鲜度，现直接选择这两列。选股备份统计也解析正文；旧版数据库继续使用原四列库存查询。外部直接 SQL 读取方需改用底座 `app.shared.snapshot_sql.PUBLISHED_SNAPSHOTS_SQL` 或接口。

2026-11-15 从真实 `0020` 旧备份恢复到一次性 PostgreSQL 17。升级前、升级后、新版 pg_dump 在另一个空库恢复后，以及原容器降级后，56 个当前指针和全部 1,864 条历史的内容、版本、业务日期与当前鲜度等元数据摘要均相同。只有 5 个当前指针共享。按相同 VACUUM FULL 口径比较两张表和全部索引，合计实际节约 5,382,144 字节。该操作仅用于一次性库的体积计量。[旧备份、版本与恢复对照](investmind-shared-snapshot-recovery.json)

部署时先将 API、作业、备份程序及直读审计更新到能读 `0020/0021` 的程序版本，再执行迁移。需要回退旧程序时，先用新版程序将数据库降级到 `20261111_0020`，将指针恢复为独立对象正文，再切回旧程序。正式应用前需对当前交付库创建并验证新的恢复点。完整归档复跑入口为底座 `scripts/audit-shared-snapshot-recovery.py <旧归档> --expected-sha256 <归档摘要>`。
